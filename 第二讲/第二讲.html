Definition of Done · 交付标准

不是“代码生成了”，而是留下五个交付物

01 / SPEC

任务卡

目标、边界、约束与验收可检查。

→
02 / BRANCH

功能分支

从最新主分支开始，不直接改 main。

→
03 / EVIDENCE

已验证 Diff

变更相关、可解释，有测试证据。

→
04 / COMMIT

清晰提交

一个完整小步骤，一段有意义说明。

→
05 / PULL REQUEST

PR 链接

别人能看懂、能复测、能提出意见。

本课的“完成”：PR 已具备评审条件，而不是 Agent 在聊天框里说了句“已完成”。
先给学生看终点，避免前半程只关注提示词。全班各自提交 PR 并完成互评，教师只选一个 PR 示范 Merge，其余保留或按约定关闭；是否被合并不作为个人完成标准。五项缺任何一项，都要能说清还差什么。

00—15 MIN · Clone & Open

第一次拿到仓库：Clone，而不是下载 ZIP

THREE ACTIONS

拿到地址，克隆，打开文件夹

  • Clone：把 GitHub 仓库及 Git 历史复制到本地，通常只做一次
  • cd：进入刚克隆下来的项目目录，后续命令在这里执行
  • 打开：在 Trae 中打开这个文件夹，而不是只打开某一个代码文件
$ git clone <教师提供的仓库地址> $ cd <克隆下来的仓库目录> $ git status
示例：仓库地址在 GitHub 页面复制。
看到“当前位于分支、工作区干净”等信息后，再用 Trae 打开该目录。
以后要取回队友更新用 git pull，不要重复 Clone。 ZIP 只是文件快照，不包含可直接继续工作的完整 Git 仓库。
现场先指认 GitHub 仓库地址、学生电脑上的本地目录和 Trae 工作区三者的关系。git clone 后面的地址由教师提供，cd 后面的目录名以实际克隆结果为准。不要让学生在仓库目录里再克隆一层；如果 git status 提示“not a git repository”，优先检查当前目录是否走错。

00—15 MIN · Repository Anatomy

打开仓库先别改代码：这些文件各有用途

README.md

项目说明书

介绍项目是什么、怎样安装、启动、测试，以及目录和协作规则。

.md 表示 Markdown 文档；GitHub 会把它渲染成易读页面。
.gitignore

忽略清单

告诉 Git 哪些文件通常不应纳入版本管理，例如依赖目录和本地配置。

常见例子：node_modules、.env、构建产物；不是加密工具。
SOURCE

源代码

实现页面、接口和业务逻辑的文件，可能位于 src、app 或其他目录。

目录名以真实仓库为准，先让 Agent 定位，不凭经验猜。
TESTS

测试文件

用可重复执行的方式检查行为，可能位于 tests 或带有 test / spec 后缀。

测试也是代码；不能为了让错误实现通过而随意放宽。
CONFIG

配置文件

记录项目命令、依赖或工具设置，例如 package.json 等。

先看 README 怎么使用；本课不新增依赖、不随意改配置。
.git/ 与 .gitignore 不是一回事：前者是保存本地版本历史的隐藏目录，不要手动改删；后者是文本忽略清单。
用练习仓库现场逐项指认，不要求学生背扩展名。特别强调 .env 可能保存密钥，不能提交；已经被 Git 跟踪的文件不会因后来写进 .gitignore 就自动取消跟踪，本课遇到此类情况交给教师处理。package.json 只是配置示例，不同技术栈可能有其他配置文件。

00—15 MIN · Read Before Run

先读 README，再在正确的目录运行命令

README.md · PROJECT GUIDE

重点找这五类信息

  1. 项目做什么、使用什么技术
  2. 第一次安装需要哪些步骤
  3. 用哪条命令启动项目
  4. 用哪条命令运行测试
  5. 目录说明、项目规则与协作要求
TERMINAL · BEGINNER RULES

看课件命令时，先懂四条约定

  • $：提示符，用来表示命令行，不需要自己输入
  • <...>：占位符，必须换成真实地址、路径或姓名
  • 当前目录：先进入仓库目录，再执行项目命令
  • 一次一行：读完输出再继续；报错先保留，不盲目重试
README 是项目入口。安装、启动和测试命令以真实仓库为准，不把课件示例当成所有项目通用命令。
教师准备的 README 至少包含环境要求、安装、启动、测试、目录说明、分支命名和 PR 规则，并确保按 README 从干净克隆可以操作。课堂演示故意指出 $ 和尖括号，避免学生原样输入。Markdown 只讲“用简单标记写标题、列表和代码块的文本格式”，不展开语法教学。

00—15 MIN · Setup & Branch

统一案例：给登录表单增加必填校验

ONE SMALL TASK

同一个仓库，同一个目标

空邮箱或空密码时，在对应字段附近显示提示，并且不发送登录请求；合法输入保持原有登录流程。

  • 不做：不改接口、不重构页面、不新增依赖
  • 依据：README、项目规则、现有登录代码与测试
  • 终点：测试通过，Diff 可解释，提交后发起 PR
$ git status $ git switch main $ git pull $ git switch -c feature/login-validation-<你的姓名拼音> $ git status
第一条 status：确认没有未提交修改。
第二条 status：确认已经位于自己的新分支。
姓名占位符必须替换，例如 zhangsan，不能照抄尖括号。
练习仓库由教师提前提供，学生不要现场新建空项目。先执行 git status；如果已有未提交修改、分支异常或远程拉取冲突，先保留现场并找教师，不要让 Agent 清理或强推。git switch main 表示切换到主分支，git pull 表示取回远程更新，git switch -c 表示创建并切换到新分支。分支名示例 feature/login-validation-zhangsan 中的 zhangsan 要换成学生自己的姓名拼音或学号，避免全班撞分支。main 以仓库实际主分支为准。

01 · SPEC BEFORE CODE

先写任务卡，
再让 Agent 动手

Spec Coding 不是额外增加一套复杂流程，
而是把目标、边界与验收写成可执行的任务说明。

01
强调小任务不需要长篇 PRD。今天的一张任务卡已经足够体现 Spec Coding 的核心：先明确完成标准，再让 Agent 实施。大任务的接口、数据迁移和架构 Spec 后续再展开。

01 · Prompt vs Task Card

Agent 容易失控，往往因为任务本身没有边界

VAGUE REQUEST

只有愿望，没有验收

“帮我完善一下登录，顺便把 UI 做得高级点，接口也优化一下。”
  • “完善”和“高级”无法客观验收
  • 页面与接口同时扩大修改范围
  • 没有项目约束，Agent 只能自行猜测
→
ACTIONABLE TASK

一次只说清一个小改动

“只增加登录必填校验：空邮箱或空密码显示对应提示，不发送请求；合法输入保持原流程。不改接口和页面结构，不新增依赖。先给计划，确认后修改，并运行现有测试。”
  • 目标、非目标和约束都能检查
  • 正常与异常路径都有完成标准
  • 计划、修改和验证有明确检查点
让学生指出左侧到底有多少个任务：表单、视觉、接口至少三个方向。右侧不是“提示词技巧”，而是工程任务说明。提示词可以短，但不能缺少关键事实和验收；长提示词也不天然等于好任务卡。

01 · Lightweight Spec

一张够用的任务卡，只要五个字段

01 / GOAL

目标

用户或系统最终应该出现什么可观察变化？

例：空表单出现字段提示，且不发送登录请求。
02 / NON-GOALS

非目标

本次明确不做什么，防止顺手扩大范围。

例：不改接口、不做注册、不 redesign。
03 / CONTEXT

项目依据

哪些文档、代码、设计和现有行为必须遵守？

例：README、项目规则、登录文件与现有测试。
04 / CONSTRAINTS

约束

技术、兼容性、安全和修改范围有哪些限制？

例：复用现有组件，不新增依赖，不做无关格式化。
05 / ACCEPTANCE

验收

哪些操作和结果能证明任务真正完成？

例：空值、单字段空值、合法输入、回归测试。
判断标准：换一位同学拿到这张卡，能否做出同一个结果，并用同一组标准验收？
验收要写可观察结果，不写“代码优雅”“体验更好”“功能正常”。如果涉及接口或数据变化，大任务还要补充请求响应、兼容策略和迁移约束；本课的小改动不展开这些字段。

01 · Case Spec

把登录校验任务写成一份轻量 Spec

GOAL / 目标

空邮箱或空密码时，在对应字段附近显示明确提示，不发送登录请求；合法输入保持原有登录行为。

NON-GOALS / 非目标

不修改后端与接口，不重构页面，不替换 UI 方案，不增加“记住我”等新功能。

CONTEXT / 项目依据

阅读 README、项目规则、登录页面与现有测试；以仓库当前实现为准，不假设目录或框架。

CONSTRAINTS / 约束

复用现有表单与样式约定，不新增依赖，不做无关格式化，不提交密钥、缓存或构建产物。

ACCEPTANCE / 验收标准

① 两项为空：显示两处提示，登录请求不发出；② 仅一项为空：只显示对应提示；③ 输入合法：原有登录流程不变；④ 新校验与既有测试均通过，页面无新增报错；⑤ Diff 只包含本任务相关文件。

执行约定：Agent 先阅读并给计划，得到确认后才能修改；如果项目事实与任务卡冲突，先停下来提问。
这页是示例，不要求机械照抄路径或技术栈。请学生注意“不发送请求”和“原流程不变”同样需要验证，不能只检查页面上出现了红字。第五项把 Diff 范围也纳入验收，防止 Agent 顺手修改无关内容。
LAB 01 · 10 MIN

实操一：完成任务卡，再互相做一次 Ready 检查

01

独立填写 · 6 分钟

参照上一页，把目标、非目标、项目依据、约束和验收写进 Trae 对话草稿或练习文档。

02

同伴互换 · 2 分钟

不讨论代码实现，只检查对方是否能据此执行和验收；找出任何模糊词或隐藏任务。

03

修订定稿 · 2 分钟

删除无关目标，补齐遗漏的异常与回归场景；此时尚不让 Agent 修改文件。

Definition of Ready

  • 只有一个可独立交付的目标
  • 非目标和禁止事项明确
  • 项目依据来自真实仓库
  • 正常、异常、回归都能验收
  • 修改前先经过计划检查点
教师巡回时只问三类问题：怎样算完成？什么不能动？你准备怎么证明？如果学生直接复制示例，要求其指出自己仓库中的 README、登录文件和测试位置，确保任务卡与真实项目连接。任务不清楚时，不进入下一阶段。

01 · Plan Gate

计划检查点：先验证理解，再授权修改

READ-ONLY PROMPT

先明确“不要改文件”

先不要修改文件。请阅读 README、项目规则以及本任务相关代码和测试，给出： 1. 准备修改的文件与原因 2. 实现步骤与可能影响 3. 要运行的测试与手工验收 4. 仍不确定、需要我确认的问题 如果任务卡与项目事实冲突，请先提问。
A REVIEWABLE PLAN

好计划能回答四个问题

  1. 找到了正确的表单、校验和测试位置吗？
  2. 修改步骤是否直接对应任务卡？
  3. 有没有接口、重构或新依赖等范围扩张？
  4. 测试是否覆盖空值、合法输入和原功能？
不通过时：补充上下文、纠正任务或要求重新定位；不要用“你看着办”代替确认。
计划不是越长越好，而是能暴露 Agent 对项目的理解。如果它计划修改后端、安装状态库或重写样式，学生应立即发现范围偏离。计划通过只代表可以开始改，不代表结果已经通过验收。

01 · Context, Rules & Tools

给 Agent 最小充分上下文，而不是塞入整个项目

TASK

本次任务

任务卡说明这次要实现什么、不做什么，以及如何验收。

随任务变化，是当前对话的核心。
PROJECT FACTS

项目事实

相关文件、目录、接口定义、现有行为和真实运行结果。

先给入口，让 Agent 继续检索；不凭记忆猜路径。
RULES

长期规则

技术栈、目录约定、代码风格、测试命令与禁止事项。

稳定事实写入项目文档或 Rules，不靠新会话记忆。
TOOLS

行动能力

Read、Search、Edit、Terminal 让 Agent 获取事实并执行修改。

Tools 负责“能够做”；Skills / MCP 今天不额外配置。
分工：任务卡管“这次做什么”，Rules 管“长期遵守什么”，Tools 管“可以执行什么动作”。
承接第一讲的分类，但只讲实操所需。Rules 不应替代任务卡，任务卡也不必重复所有项目长期规则。Skills 是可复用任务指导，MCP 是外部能力接入协议；它们不是今天完成任务的先决条件，避免课堂转向插件安装。

用证据验收

Agent 可以连续推进，
但人始终保留计划、权限、Diff 和验证四个检查点。

02 · Permission Decisions

每一次工具调用，都做“继续、暂停、拒绝”判断

动作课堂示例你的判断决定
Read / Search读取 README、登录代码、测试与项目规则是否限制在项目工作区？是否涉及无关敏感文件？通常继续
Edit / Create编辑校验逻辑、样式和本任务测试文件与计划一致吗？是否出现大面积重写或删除？先看范围
Terminal运行 README 中的测试、启动或检查命令命令是否看得懂？会改系统、删数据或访问外部服务吗？逐条确认
Install / Delete新增依赖、删除目录、清理工作区本任务已经明确禁止；不能用“为了完成”自行扩大授权。本课拒绝
Network / Push上传代码、操作远程仓库或第三方服务数据去哪里？远程分支与提交是否已核对？单独确认
原则：不懂的命令不批准；任务卡没有授予的新范围，不因 Agent 建议而自动扩大。
读取也可能接触敏感信息，因此不是绝对无风险。Terminal 不等于危险，也不等于安全，要看具体命令。本课明确禁止安装依赖和删除目录，是为了练习识别范围扩张，而不是说真实开发永远不能做这些事。

看 Agent 如何根据工具结果推进，而不是只看最后回答

01 / OBSERVE

Read / Search

定位真实代码、规则和测试，补足当前任务上下文。

02 / ACT

Edit

按照已确认计划做小步修改，保留原项目约定。

→
03 / CHECK

Terminal

运行测试或检查，获得真实成功输出或完整报错。

→
04 / CONTINUE

修正或停止

根据结果继续小步修复；范围异常时停止并请求确认。

突然重写多个无关模块
批量移动或删除文件
要求安装依赖或修改系统
读取密钥或执行不明外部操作
这里只建立可观察的执行循环，不讲 ReAct 名称或内部算法。学生应能说出 Agent 正在读什么、为什么改这个文件、刚运行的命令产生了什么结果。出现停止信号时，先保留现场，不要继续多轮自动修复。

02 · Debug Feedback

调试不是反复说“还是不行”，而是补齐失败证据

LOW-INFORMATION FEEDBACK
“不行。”
“还是报错。”
“你再修一下。”

Agent 无法从这些回复中知道：你做了什么、期望什么、实际发生了什么。

REPRODUCIBLE FEEDBACK

一次反馈带齐五项

  1. 复现步骤：从哪个页面、输入什么、点击什么
  2. 期望结果：根据任务卡，本来应该怎样
  3. 实际结果：页面、状态或请求实际怎样
  4. 完整报错：保留命令、关键堆栈与失败用例
  5. 范围约束：只定位本次问题，不借机重构
反馈模板：“按步骤 A 操作，期望 B，实际 C；完整报错如下。请只分析与当前任务相关的原因，先给修复方案再继续。”
报错要复制真实输出，不让学生编造或只截最后一行。若失败原因超出当前任务，例如需要升级框架或改后端，应停止并更新任务边界，而不是让 Agent 无限扩张修复范围。

实操二：让 Trae 实施，并停在候选 Diff

01

发送任务卡，先审计划

确认文件、步骤和测试都对应任务；发现范围扩张先纠正，再允许修改。

02

监督 Read / Edit / Terminal

看清每次关键动作；失败时提交复现步骤、期望、实际和完整报错。

03

Agent 报告完成后先停住

不要立即 Commit，也不要继续加需求；保留当前修改，进入人工 Diff 和验收。

三个课堂检查点

  • 计划已确认，没有擅自改接口
  • 变更仍集中在登录校验与测试
  • 没有安装依赖或不明外部操作
  • 测试输出和遗留问题已保留
  • 尚未提交，准备人工验收
教师巡回优先检查计划偏离和权限，不要直接替学生修改代码。进度快的学生也不能顺手增加“邮箱格式校验”“密码强度”等未写入任务卡的需求。进度慢的学生至少保留真实报错和当前 Diff，便于复盘。

03 · TEST & VERIFY

不是“能跑”，
而是有证据证明正确

测试比较“期望结果”和“实际结果”。
选对测试层级、设计有效场景、保留可复测证据。

03
先纠正“页面能打开就算完成”的直觉。测试不是 Agent 最后随口报告的一句通过，而是从任务卡的验收标准推导出的检查。这里的分类会比较多，教学生按“测什么、怎么测、在哪个阶段测”建立地图，不要求背术语。

03 · Testing Map

同一个测试可以同时属于多个分类

01 / EXECUTION

静态 / 动态

静态测试不运行程序：审查需求、代码、类型与 Lint；动态测试实际运行并观察行为。

代码评审也是质量活动，不等同于动态测试。
02 / KNOWLEDGE

黑盒 / 灰盒 / 白盒

黑盒只看输入输出；灰盒结合部分内部信息；白盒依据分支、语句和内部结构设计用例。

用户验收偏黑盒，单元测试通常偏白盒。
03 / SCOPE

测试范围

从一个函数，到模块协作、接口、完整用户流程；范围越大越接近真实使用，定位失败通常也越难。

不是只做最大的 E2E 就万无一失。
04 / PURPOSE

功能 / 非功能

功能测试问“是否做了该做的事”；非功能测试问“速度、安全、兼容性、易用性等是否达标”。

登录能成功是功能，响应是否足够快是非功能。
05 / EXECUTOR

手工 / 自动化

手工测试适合探索、体验和一次性确认；自动化适合重复、稳定、需要频繁回归的检查。

自动化的是检查过程，不是免去人的判断。
06 / STAGE

开发 / CI / 验收 / 发布

开发时快速反馈；提交 PR 后由 CI 复测；业务方做 UAT；发布前后做冒烟与线上监测。

CI 是自动执行检查的持续集成环境。
用同一个登录例子串起来：阅读校验函数属于静态检查；运行函数属于动态测试；只从页面输入属于黑盒；依据 if 分支补用例属于白盒。强调分类之间不是互斥选项，例如“PR CI 中自动运行的黑盒 E2E 功能回归测试”完全合理。

03 · Diff Review

Diff 审查：每一处修改都要能对应任务

登录校验逻辑 · 教学示意
function validateLogin(form) { - return true; + const email = form.email.value.trim(); + const password = form.password.value; + if (!email) showError('email', '请输入邮箱'); + if (!password) showError('password', '请输入密码'); + return Boolean(email && password); }

按顺序问五个问题

  • 新增与删除分别意味着什么？
  • 每处变化对应哪条验收标准？
  • 是否出现无关文件或大面积格式化？
  • 是否误删原逻辑、引入密钥或调试残留？
  • 测试是否也修改了，修改是否合理？
红色删除行同样要看。不理解的变化先问 Agent 或同学，不能因为“测试绿了”就跳过 Diff。
左侧仅用于教学生读 added / removed / context，不要求他们的实现与示例一致。重点演示为什么 return true 被删除、为什么新增空值判断与合法返回。若 Agent 修改测试只是为了让错误实现通过，要回到任务卡判断测试是否被不当放宽。

03 · Test Levels

测试金字塔不是背比例，而是组合不同反馈

层级检查什么登录案例擅长与盲区
静态检查语法、类型、格式、可疑代码Lint 发现未定义变量快；不能证明运行行为正确
单元测试 Unit独立函数或最小模块不同输入调用 validateLogin快且易定位；外部协作常被隔离
组件测试 ComponentUI 组件渲染与交互点击登录后显示字段提示贴近用户；未必经过真实后端
集成测试 Integration多个真实模块能否协作表单、校验、请求模块一起运行发现接线问题；环境准备更多
API / 契约测试状态码、字段及双方数据约定合法请求仍符合原登录接口稳定检查边界；不等于完整 UI
端到端 E2E真实系统中的关键用户旅程浏览器输入、提交并观察结果最接近用户；较慢且更易受环境影响
选择原则：能在低层准确验证的规则不必全靠 E2E；跨模块接线和关键用户流程也不能只靠单元测试。
金字塔强调通常多写快速、稳定的小测试，少写昂贵的大测试，但不是固定数量指标。契约测试可理解为消费者与提供者对请求响应约定的检查，本课只需知道它解决“前端以为后端会返回什么”的不一致。本任务已有前端校验，至少要运行现有测试、补相关单元或组件测试，并做一次真实手工流程。

03 · Functional Testing

这些名字回答的是“为什么现在测”

01 / FUNCTIONAL

功能验证

依据需求检查正常、异常和边界行为，确认产品做了约定的事。

两项为空时显示对应提示，且不发送登录请求。
02 / SMOKE

冒烟测试

用少量关键检查判断这个版本是否值得继续深入测试。

页面能打开、表单能操作、核心流程未整体坏掉。
03 / SANITY

健全性测试

小改动后，快速确认相关功能确实按预期工作。

只修提示文字后，重点检查对应字段提示。
04 / REGRESSION

回归测试

修改代码后，重测已有能力，防止旧功能被新变化破坏。

合法输入仍走原登录行为，相关页面无新增错误。
05 / ACCEPTANCE / UAT

验收测试

按业务目标与验收标准判断能否交付；UAT 由用户或业务代表参与。

逐条核对任务卡，而不是由开发者自行改标准。
06 / EXPLORATORY

探索性测试

带着目标边学习边设计边执行，寻找固定用例没有想到的问题。

尝试连续点击、切换字段、刷新等合理操作并记录发现。
再测试 Retest ≠ 回归 Regression：再测试确认已知缺陷已修好；回归检查这次修改有没有破坏其他已有行为。
Smoke 与 Sanity 很容易混淆：Smoke 偏版本整体能否继续测，Sanity 偏局部修改是否合理；两者通常都是窄而快，但目的不同。回归不是某个特定工具，任何层级的旧用例都可用于回归。探索性测试不是随便乱点，也要有范围、记录和结论。Retest 要复用能复现原缺陷的场景，Regression 则选择相关旧能力；Agent 修完一个失败用例后，两者都需要考虑。

03 · Quality Attributes

功能正确之外，还要问“用得怎样”

01 / PERFORMANCE

性能测试

响应、吞吐与资源使用。负载看预期压力，压力找极限，尖峰看突增，浸泡看长时间稳定。

02 / SECURITY

安全测试

认证、授权、输入处理、敏感信息与依赖漏洞。只对明确授权的系统开展安全测试。

03 / COMPATIBILITY

兼容性测试

不同浏览器、系统、设备、屏幕或版本下，功能与展示是否仍符合要求。

04 / RELIABILITY

可靠性与恢复

故障、重试、超时后能否稳定工作；备份与恢复是否真正可用，而不只是“有备份”。

05 / USABILITY

易用性测试

用户能否理解、完成和纠错。观察真实操作，不只问开发者觉得是否方便。

06 / ACCESSIBILITY

无障碍测试

键盘操作、焦点、语义、对比度及辅助技术能否支持更多用户完成任务。

07 / I18N / L10N

国际化与本地化

国际化检查多语言适配能力；本地化检查具体语言、日期、货币和文化习惯。

08 / OPERATIONS

安装升级与迁移

安装、升级、降级、数据迁移与配置变化是否可控，失败时能否恢复。

性能的几个子类只需建立直觉：Load 是预期负载，Stress 是逐步超过正常水平寻找极限，Spike 是突然高峰，Soak 是长时间运行观察泄漏和退化。本任务没有性能或安全指标，不要为了“测得全”擅自制造验收要求；让学生知道未来任务卡出现这些质量目标时应选择相应测试。

03 · Test Design

好测试来自规则，不是随机多敲几组输入

等价类划分把预期表现相同的输入分组，从每组选代表，减少无意义重复。
边界值分析重点检查规则交界处；本例是“有内容 / 无内容”，不是凭空增加长度限制。
决策表把多个条件组合与对应结果列全，避免漏掉“只有一项为空”。
状态 / 场景测试按操作路径检查状态变化，如输入、提交、提示、修正后再次提交。
邮箱密码期望结果
空空两处提示；不发送登录请求
空非空提示邮箱；不发送登录请求
非空空提示密码；不发送登录请求
非空非空无必填错误；原登录行为不变
每条用例写清：前置条件 → 操作与数据 → 期望结果。实际结果与期望不一致时，先保留证据再定位。
右表是两条件必填规则的决策表，同时覆盖空与非空等价类。本课只有必填校验，不要把“邮箱格式错误”“密码至少八位”“纯空格如何处理”等未确认规则塞给 Agent。若学生发现需求不清楚，正确动作是提出并更新任务卡，而不是测试和实现各自猜一套。

03 · Test Trust

绿色勾号不等于需求已被证明

01 / COVERAGE

覆盖率

语句、分支等覆盖率说明哪些代码被执行，不说明断言是否有效，也不等于需求覆盖完整。

02 / TEST DOUBLE

Stub / Mock / Fake

Stub 提供预设回答，Mock 还检查交互，Fake 是简化可工作的替代实现；用来隔离外部依赖。

03 / FLAKY

不稳定测试

同一代码时通过、时失败，常与异步、时间、顺序或共享环境有关；要定位原因，不靠无限重试掩盖。

04 / TRIAGE

失败先分类

可能是产品缺陷、测试本身错误、环境或数据问题。先复现并看完整日志，再决定改哪里。

禁止“为绿而绿”：不能删除关键断言、放宽期望、跳过失败用例，或把真实缺陷标成无关问题，只为让 Agent 报告通过。
举例：原测试期望不发送请求，实现却有请求，此时把断言改成允许请求就是篡改验收。若测试环境缺依赖，错误信息应明确写环境缺什么，而不是声称源代码已正确。测试替身能提升稳定性，但替代过多也会漏掉真实集成问题，所以仍需适量集成或 E2E。

03 · Agent + CI

把“验收标准”翻译成“测试矩阵与证据”

01 · DESIGN编码前列场景：正常、异常、边界、回归；选择最低但足够的测试层级。
02 · IMPLEMENT实现与测试可以交给 Agent，但你审核它是否改了需求、断言和无关代码。
03 · VERIFY在干净环境运行真实命令；失败时保存完整输出，区分产品、测试和环境问题。
04 · CI / PRPush 后 CI 独立复测；检查 PR 状态与日志，本地通过不保证 CI 也通过。
可直接给 Agent 的验证指令 
只依据任务卡验收标准：
1. 先列测试矩阵，不修改需求
2. 优先复用仓库现有测试方式
3. 运行相关测试及必要回归
4. 报告实际命令、结果与遗留问题
5. 失败先诊断，不得删断言或放宽期望
证据包：测试矩阵、命令与退出结果、关键日志、手工场景记录、CI 链接；截图只是辅助。
强调验证独立性：生成代码的 Agent 可以自己运行测试，但人必须审查测试是否对应原始验收，最好让 CI 在另一环境复跑。不要要求 Agent 编一个漂亮结果。退出码为 0 也要看是否真正执行了目标测试，例如“0 tests”不能被描述成功能已验证。
LAB 03 · 12 MIN

实操三：从任务卡生成测试矩阵，留下真实证据

01 / AUTOMATED

自动化测试

  • 命令以 README 和项目规则为准
  • 运行现有测试与本任务测试
  • 核对执行数量、结果和失败信息
示例入口：npm test
若仓库命令不同，以实际项目为准。
02 / MANUAL

手工验收

  • 两项为空：两处提示，无登录请求
  • 仅一项为空：对应提示正确
  • 合法输入：原登录行为不变
必要时看浏览器控制台与网络请求，不只看页面文字。
03 / REGRESSION

回归与遗留

  • 相关页面没有新增运行报错
  • 原有测试没有被无意放宽
  • 未解决问题如实写入 PR，不隐藏
记录命令、实际结果、CI 状态；“Agent 说通过”不是证据。
完成标准：每条验收标准至少有一种检查对应；每个失败都有真实结论，而不是被隐藏。
先让学生用两分钟把四种输入组合映射到自动化或手工检查，再执行。教师巡视时重点看是否只测合法输入、是否检查网络请求、是否把未运行写成通过。本课不追求高覆盖率，也不要求所有非功能测试都执行；选择与任务风险相称的组合并保留可复测证据。

04 · DOCKER & ENVIRONMENT

让运行环境
也能被描述与复现

代码相同，不代表依赖和配置相同。
Docker 把应用及其运行环境打包，减少“我电脑上能跑”。

04
从测试自然过渡：本地通过而 CI 失败，可能是运行时版本、系统依赖、环境变量或数据不同。Docker 是提高环境一致性和可复现性的工具，但不能自动修复错误代码，也不能替代测试。本课只建立单机容器与 Compose 基础，不讲 Kubernetes。

04 · Why Docker

容器解决环境问题，不代替代码管理与测试

01 / CONTAINER

Docker 容器

把应用、运行时和系统依赖放在隔离环境中运行，让开发与 CI 使用一致配置。

适合复现项目环境、运行服务和自动化测试。
02 / VIRTUAL MACHINE

与虚拟机的区别

虚拟机通常虚拟整套操作系统；容器共享宿主机内核，只隔离进程及其文件、网络等视图。

容器通常更轻量，但隔离边界和适用场景不同。
03 / GIT

与 Git 的区别

Git 管理源代码版本；Docker 描述并运行环境。Git 提交不会自动带上本机全部依赖和配置。

常见组合：Git 保存 Dockerfile，Registry 保存镜像。
收益：环境一致、依赖隔离、启动可重复、清理更明确。代价是新增配置与学习成本，小项目不必为了使用 Docker 而使用。
避免说“容器就是轻量虚拟机”，这只能帮助粗略入门，原理上容器是宿主机上的隔离进程。Linux 容器依赖宿主机内核；Windows 上通常通过 Docker Desktop 与 WSL2 运行 Linux 容器。镜像能减少环境差异，但外部服务、密钥和数据仍需正确配置。

04 · Core Objects

Dockerfile → Image → Container，Registry 负责分发

01 / DOCKERFILE

构建说明

文本文件，声明基础镜像、复制文件、安装依赖、端口与启动命令。

docker build -t login-demo .
02 / IMAGE

镜像

按层组成的只读应用模板，包含运行所需文件与元数据；镜像本身不是正在运行的程序。

docker images
03 / CONTAINER

容器

镜像的运行实例，有自己的进程、网络和可写层。同一镜像可创建多个容器。

docker run <镜像>
04 / REGISTRY

镜像仓库

集中存储和分发镜像，例如 Docker Hub 或私有 Registry；标签用于标识版本。

docker pull / push
类比只帮助记忆：Dockerfile 像配方，Image 像可复制的成品模板，Container 像正在运行的实例；最终以实际对象为准。
用 build、run 两个动作区分镜像和容器：build 的输出是镜像，run 根据镜像创建并启动容器。容器删除后其可写层通常随之删除，需要保留的数据应使用卷。tag 不是 Git 分支；latest 也只是普通标签，不保证内容稳定，团队项目宜使用明确版本。

04 · Runtime Wiring

容器启动后，还要接好端口、数据、网络与配置

01 / PORT

端口映射

容器端口默认不等于宿主机端口。用 -p 8080:80 把宿主机 8080 转发到容器 80。

浏览器访问宿主机的 localhost:8080。
02 / VOLUME

命名数据卷

由 Docker 管理的持久化数据空间，适合数据库等需要跨容器保留的数据。

-v app-data:/data；卷与容器生命周期分开。
03 / BIND MOUNT

目录绑定挂载

把宿主机指定目录映射进容器，常用于开发时同步源代码。

容器会直接影响该目录，授权前必须核对真实路径。
04 / NETWORK

容器网络

同一用户定义网络中的容器通常可用服务名通信，不必都暴露到宿主机。

容器里的 localhost 通常指容器自己。
05 / ENV

环境变量

用 -e NAME=value 或 env 文件传入环境配置，让同一镜像适配不同环境。

配置改变行为，但不等于保存业务数据。
06 / SECRET

密钥边界

密码与令牌不能写进镜像、Git 或课件。环境变量也可能被日志或 inspect 暴露。

课堂只使用占位值；真实项目采用团队秘密管理方案。
重点演示宿主机端口在左、容器端口在右。命名卷如 app-data 与绑定宿主目录不同，前者由 Docker 管理，后者直接对应用户目录。停止或删除容器不等于删除命名卷，但 docker compose down -v 会删除 Compose 声明的卷，因此本课禁止学生随意执行。Windows 路径包含盘符和空格时更需谨慎，优先使用项目图形界面或教师给出的命令。

04 · Command Map

先观察，再启动；先看日志，再改变状态

目的命令示例作用与注意
检查安装docker version / docker info确认客户端与服务端是否可用，info 可看环境信息
查看对象docker ps -a / docker images看全部容器 / 本机镜像；不加 -a 只看运行中容器
构建镜像docker build -t login-demo .末尾点号表示当前目录是构建上下文
创建并启动docker run -d --name login -p 8080:80 login-demo-d 后台运行，--name 命名，-p 映射端口
查看日志docker logs login诊断启动与应用输出；需要持续观察可加 -f
进入执行docker exec login <命令>在已有容器执行命令；交互终端常加 -it
停止 / 再启动docker stop login / docker start login停止运行 / 启动已存在容器，不是重新 build
删除容器docker rm login删除指定容器；先确认数据已持久化且对象无误
命令中的 login-demo、login、端口都要替换为项目实际值。docker start 不会自动使用最新代码或镜像，修改 Dockerfile 后通常要重新 build 并重建容器。删除容器前先检查挂载和数据，不要为了“清理干净”执行批量 prune。本页仅作命令地图，课堂由教师演示，不要求学生背下所有参数。

04 · Docker Compose

Compose 用一份 YAML 管理一组容器

compose.yaml · 教学示意 
services:
  web:
    build: .
    ports:
      - "8080:80"
    volumes:
      - app-data:/data

volumes:
  app-data:
service 是一项应用服务；这里只有一个 web。声明的 app-data 是命名卷，删除容器后仍可保留数据。
UPdocker compose up -d --build：重新构建并后台启动服务。
OBSERVEdocker compose ps 与 docker compose logs：检查状态和日志。
TESTdocker compose exec web <测试命令>：在相同环境运行测试。
DOWNdocker compose down：停止并移除本组容器与默认网络，不要加 -v。
.dockerignore：排除构建上下文中的无关或敏感文件，例如依赖目录、日志与本地秘密；它控制发给构建的内容，不等于 .gitignore。
Compose 适合一条命令启动应用、数据库等多个关联服务，也可用于单服务统一参数。YAML 缩进有意义，不能用 Tab 随意替换。up -d --build 会改变本机容器状态并可能下载镜像，应由学生确认后执行。down 默认不删除命名卷，down -v 会删除卷，课堂明确禁止。compose.yaml 应结合项目真实启动命令修改，示例不要求学生照抄运行。

04 · Agent Boundaries

让 Agent 操作 Docker，也要先分清观察与变更

PERMISSION BOUNDARY
可先看阅读 Dockerfile / Compose；version、info、ps、images、logs 用于观察。
先确认build、pull、up、run、exec 会下载、构建或改变运行状态，确认对象与范围。
需审批stop、rm、down 会影响服务和数据；操作前说明影响，得到明确批准。
本课禁止prune、down -v、--privileged、挂载 docker.sock；不批量清理，不扩大权限。
FAILURE → NEXT CHECK
无法连接 Docker先确认 Docker Desktop / 服务已启动
端口被占用查 ps 和端口占用，换端口前先确认
启动后退出看 ps -a 与完整 logs，不反复盲重启
页面打不开分清宿主机 / 容器端口和应用监听地址
修改未生效区分 bind mount、镜像重建与容器重建
数据消失立即停止清理，检查卷与挂载，不继续 down -v
Windows 学生先启动 Docker Desktop，并确认 WSL2 集成按教师环境配置完成；不要把安装故障误判为代码错误。Agent 只读日志通常风险低，但日志也可能含敏感信息，不应外发。exec 并非天然只读，里面运行的命令可能修改文件或数据库，所以也要看具体内容。任何清理命令都必须指定对象，不允许为了让环境“干净”而全量 prune。

05 · COMMIT & COLLABORATE

把修改变成
团队交付

Commit 留下清晰历史，Push 同步功能分支，
PR 让修改理由、验证证据与评审意见进入共同记录。

05
现在才进入提交，确保学生已经把 Agent 修改与验收分开。Git 命令可以继续由学生自己执行；如果让 Agent 代为执行，也要核对当前分支、工作区和命令范围。

05 · Atomic Commit

只提交这一个经过验证的改动

01 / STATUS + DIFFstatus 看当前状态，diff 看尚未暂存的修改。
02 / ADDadd 把选定文件放入“暂存区”，只选择本任务文件。
03 / CACHED DIFFdiff --cached 检查暂存区，即真正即将提交的内容。
04 / COMMITcommit 在本地保存一次版本快照，说明具体行为。
$ git status $ git diff $ git add <登录文件> <测试文件> $ git diff --cached $ git commit -m "feat: add login form validation" $ git status
把 <登录文件>、<测试文件> 替换为真实路径，不能照抄尖括号。
-m 后面的引号内容是提交说明；最后再次检查是否漏交或误交文件。
用“暂存区”解释 git add：它不是提交，也不是把所有文件放进去的固定仪式，而是选择本次交付范围。Commit 此时只保存在学生本机，还没有上传 GitHub。提交信息遵循仓库现有约定，本页使用 feat 前缀作为示例。若 git status 显示其他修改，不要盲目清理或一并提交，先辨别来源。

05 · Push & Pull Request

Push 上传功能分支，PR 说清“为什么与怎么测”

$ git push -u origin feature/login-validation-<你的姓名拼音>
分支名必须与前面创建的一致，并替换姓名占位符。
origin 是远程仓库别名；-u 记住对应关系，之后本分支可直接 git push。
PR TITLE

feat: add login form validation (<你的姓名拼音>)

base：main，修改准备进入的目标分支。
compare：自己的功能分支，装着本次提交。

PR DESCRIPTION 
## What
- 增加邮箱和密码的必填校验与字段提示

## Why
- 避免空表单触发无效登录请求

## How to test
- 填写实际测试命令、环境（本机 / Docker / CI）与真实结果
- 手工覆盖：两项为空 / 单项为空 / 合法输入

## Scope & notes
- 未修改接口，未新增依赖
- 如实填写已知限制；没有则写“无”
Push ≠ Merge：Push 只把本地 Commit 上传到远程功能分支；经过 PR、评审和 Merge 后，修改才进入目标分支。本课不直接推 main，也不使用 force push。
现场带学生核对 GitHub 的 base 与 compare，方向应是“自己的功能分支 → main”，不能选反。PR 描述不要复制 Agent 的长篇总结，也不要只写 update。测试证据必须填学生自己的真实结果，不能照抄课件占位文字。若课堂仓库使用 dev 作为集成分支，以团队规则为准。GitHub 页面按钮可能更新，但 What / Why / How to test 三类信息长期有效。
LAB 04 · 12 MIN

实操四：互评 PR，并在原分支上完成一轮修改

01 / REVIEW

两人互换 PR

对照任务卡、Diff 和证据留下具体评论，指出文件、场景与问题，不只写“这里不对”。

02 / REVISE

本地修改

作者理解评论后小步修复；若意见会扩大需求，先讨论任务边界。

03 / VERIFY

重新验证

再次运行相关测试与手工场景，更新验证证据。

04 / SYNC

提交并 Push

仍在原功能分支新增 Commit，再次 Push，原 PR 自动更新，不另开 PR。

05 / RESOLVE

教师示范 Merge

课堂只选一个 PR 示范合并；其余保留或关闭，不要求全班全部 Merge。

评审对象是实现，不是同学。无论代码由人还是 Agent 生成，作者都要能解释、验证并继续修改。
两人一组互换 PR：至少提出一条有依据的问题，或明确说明检查了哪些项目后没有发现问题。若没有真实修改需求，可由教师提供一条统一评论，例如“单项为空时是否只显示对应提示？请补证据”，让学生练习补充测试或说明后，在原分支 Commit、Push。解释 Merge 是把功能分支的修改合入 base 目标分支。由于全班修改同一登录文件，课堂只选一个 PR 示范 Merge；其余 PR 保留供查看或按约定关闭，不要求全部合并，避免连续冲突。Approve / Merge 按教师仓库权限安排。

Final Check · Deliver & Explain

最后不只看 PR 链接，还要能解释交付过程

个人交付清单

  • 五字段任务卡已保存
  • 个人分支来自最新 main，名称含本人标识
  • Diff 只含本任务相关变化
  • 能解释测试层级与场景选择，证据真实可复测
  • 能区分镜像与容器，理解端口、卷及 Docker 操作风险
  • Commit 说明具体、范围单一
  • PR 写清 What / Why / How to test
  • 已与同伴互评，并在原分支更新原 PR
情境 ① Agent 说“全部测试通过”，但没有命令和输出。可以验收吗？
情境 ② 实施中发现必须修改后端接口。直接让 Agent 继续做，还是先更新任务边界？
情境 ③ Reviewer 要求修改。需要关闭旧 PR、建新分支和新 PR 吗？
情境 ④ Agent 为让测试变绿，删除了“不发送请求”的断言。可以接受吗？
情境 ⑤ Agent 提议执行 docker compose down -v 清理环境。先确认什么？
情境 ⑥ 已 Push 到功能分支，能否对队友说“代码已经进 main”？
本课方法：把任务写清、把行动看清、把结果测清、把交付说清。
参考答案：① 不可以，需要真实可复测证据；② 先停止并更新任务卡/Spec，重新确认范围与验收，不能静默扩大；③ 通常不需要，在同一功能分支提交并 Push，原 PR 会更新；④ 不接受，断言对应原验收，不能用改测试掩盖产品缺陷；⑤ 不能直接执行，-v 会删除 Compose 卷，应先确认数据、备份与影响，本课不执行；⑥ 不能，Push 只是同步远程功能分支，进入 main 还需要目标分支合并。最后按左侧清单收取任务卡、个人 PR 链接和互评记录；课堂验收不以“全班 PR 都已 Merge”为条件。
LESSON 02 / COMPLETE

把任务写清楚，
把交付做扎实。

Agent 负责加速行动，你负责边界、证据与结果。
