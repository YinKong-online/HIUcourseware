01 · Mental Model

Vibe Coding：你负责目标、约束与验收，Agent 在授权范围内规划与执行

不是让 AI 在聊天框里“写一段代码”，而是让它在真实项目中完成一个可验证任务。

YOU / 01

描述目标

说清楚做什么、项目约束、不能动什么、怎样算完成。

→
AGENT / 02

规划并行动

读取项目、修改文件、调用终端，再根据结果继续调整。

→
YOU / 03

审查并验收

看计划和 Diff，检查命令，运行测试，决定接受或返工。

Agent 可以执行开发动作，但不能替你承担结果。 能否交付，仍取决于你的判断与验证。
把“生成代码”与“完成任务”区分开。Agent 的价值是能在项目里连续采取行动，但行动越多，越需要权限控制、差异审查和运行验证。

01 · Completion vs Chat vs Agent

补全、聊天、Agent：不是同一种工具

AUTOCOMPLETE

代码补全

根据当前位置预测下一段代码，适合加速局部输入。

  • 你看文件，它猜后续
  • 通常围绕当前光标
  • 不会独立完成整个任务
人：始终逐行主导实现
CHAT

聊天式助手

根据对话生成解释、方案或代码片段，结果需要你自己集成。

  • 你提问，它给回答
  • 你复制代码并处理依赖
  • 你手动运行，再把报错贴回去
人：负责搬运、执行和串起步骤
CODING AGENT

编程 Agent

围绕目标在项目内连续执行动作，并根据工具结果调整后续计划。

  • 读取目录和多个文件
  • 编辑代码、运行命令和测试
  • 根据真实输出继续修复
人：定义任务、授权、审查与验收
VS Code 是编辑器，不天然等于 Vibe Coding；Cline 等扩展之所以属于 Agent，是因为它们能跨文件读写并执行命令。Trae、Cursor 等工具也包含编辑器界面，但我们学习的是其中的 Agent 工作方式。

02 · Three Layers

先分清三层：模型、模型服务、编程 Agent

模型名和工具名不是一回事；Agent 的能力也不只取决于模型。

RAW MODEL / 01

基础模型

提供理解、推理和生成能力。模型本身不直接拥有你的项目文件、终端或工具权限。

→
MODEL SERVICE / 02

模型服务

把模型包装成可调用的服务，处理 API、鉴权、计费和限流，并暴露上下文等服务限制。

→
CODING AGENT / 03

编程 Agent

接入模型服务，再组织上下文、工具、权限和循环，在真实项目中连续完成任务。

同一个模型可以被不同 Agent 使用，同一个 Agent 也可能切换模型。 模型强，不等于整个编程系统一定好用。
这里不讲训练、参数量或模型部署细节，只建立分层。Model Service 是模型能力的托管调用入口；Coding Agent 则加入项目工作区和行动能力。下一页再看 Trae、DSH、Codex、Claude Code 等产品形态，强调产品更新很快，不背按钮和价格。

02 · Agent Anatomy

换哪个产品，Agent 都绕不开这四个部分

MODEL

模型

负责理解、推理、规划和生成候选修改。

  • 理解自然语言任务
  • 决定下一步做什么
  • 生成代码与解释
CONTEXT

上下文

决定模型此刻能看到哪些项目事实和约束。

  • 相关文件与目录
  • 需求、报错和文档
  • 项目规则与历史对话
TOOLS

工具

让模型从“给建议”变成“对项目采取行动”。

  • Read / Edit / Search
  • Terminal / Browser
  • Web / MCP 外部工具
HARNESS + LOOP

运行框架与循环

组织上下文和工具，把执行结果交回模型，直到完成或停止。

  • 权限与会话管理
  • 观察 → 行动 → 结果
  • 继续、停止或请求确认
模型只是 Agent 的一部分。 工具、上下文和运行循环，决定了它能否在真实项目里稳定工作。
结构依据[cite:1][cite:8][cite:3]
这页是后续 Agent 开发课的入口。DSH 官方把 Model 与 Harness 区分开，Cursor 官方则用 Instructions、Tools、Model 描述 Agent。课堂上用统一语言归纳成 Model、Context、Tools、Harness + Loop，不要求新人现在实现。

02 · Software Lifecycle

Agent 能参与开发，但软件不只有“写代码”

01

需求

明确给谁用、解决什么、不做什么、怎样算完成。

产出：任务卡 / Spec
02

设计

确定页面、交互、接口和数据库结构。

产出：设计与验收细则
03

开发

人与 Agent 实现功能并完成联调。

产出：候选代码
04

测试

验证正常、异常和边界情况。

产出：测试证据
05

部署

把程序发布到别人可以访问的环境。

产出：可访问版本
06

维护

修复问题，根据反馈继续迭代。

产出：下一个版本
小任务写清任务卡，大任务先形成 Spec。 Vibe Coding 是协作方式，Spec 是需求与验收载体，两者不矛盾。
Spec Coding / Spec-Driven Development 在今天只建立概念：小任务至少有目标、边界和验收标准；大任务或高风险修改先写 Spec，包括目标、非目标、约束、涉及模块、接口或数据变化以及验收方式。详细模板和编写练习留到第二讲。强调先设计再开发，“Agent 说完成”不等于通过验收。

03 · The Loop

每一次 Agent 任务，都走完这四步

任务要可验收，上下文要相关，行动要可见，结果要有证据。

01

给任务与验收

描述目标、限制、涉及模块，以及必须通过的检查。

OUTPUT一个边界清楚的小任务
02

补上下文看计划

提供相关文件、设计文档和规则，先确认 Agent 理解正确。

OUTPUT一份可审查的执行计划
03

监督工具与 Diff

看它读了什么、改了什么、运行了什么，谨慎批准敏感操作。

OUTPUT一组可解释的代码变更
04

运行验证再提交

执行测试和手工验收，确认没有破坏原功能，再做 Git 提交。

OUTPUT一个有证据的可交付版本
结果不符合预期？把完整报错 + 期望结果 + 实际结果交回 Agent，进入下一轮
Trae 的 SOLO、Codex 和 Claude Code 都能自动推进很多步骤，但人的检查点不能消失。尤其是修改数据库、删除文件、安装依赖和访问外部服务时，要先看行动范围。

03 · Context & Capabilities

Agent 的上下文与能力扩展

CONTEXT

上下文

当前任务需要的事实：相关代码、设计文档、接口定义、报错和运行结果。

原则：给相关信息，不是无脑塞入整个项目；让 Agent 能继续检索。
RULES / INSTRUCTIONS

项目规则

长期约束：技术栈、目录约定、代码风格、测试命令和禁止事项。

常见载体：AGENTS.md、CLAUDE.md、Trae Rules 等，名称随工具而不同。
SKILLS

可复用技能

把某类任务的流程、说明、脚本和资源打包，在合适场景重复调用。

它更像“可复用的任务作业指导书”，可以指导 Agent 调用工具。
TOOLS + MCP

工具与接入协议

Tools 是 Read、Edit、Terminal 等具体动作；MCP 是接入外部工具和数据源的统一协议。

MCP 本身不是一个具体工具；Server 配置、权限与安全后续单独讲。
Skill 告诉 Agent“怎么做”，Tools 让它“能够做”，MCP 负责“把外部能力接进来”。 当前会话不等于可靠的长期记忆。
官方资料[cite:2][cite:7][cite:4]
上下文解决“知道什么”，规则解决“遵守什么”，Skills 封装“某类任务怎么做”，Tools 是“具体能执行的动作”，MCP 是“外部能力的接入协议”。新会话不一定记得旧会话；稳定项目事实和决策应进入文档或 Rules，可复用经验沉淀为 Skill。复杂长期记忆和 MCP 配置留到后续。

03 · Permissions & Safety

Agent 能行动，就必须有权限边界

READ

读取

读目录、文件和日志。通常风险较低，但敏感文件本身也可能包含密钥和个人信息。

检查：它能读哪些目录？不要把无关密钥、私人资料放进项目工作区。
EDIT / DIFF

修改

创建、编辑和删除文件。接受结果前先看 Diff，确认修改范围没有失控。

检查：改了什么、为什么？无关格式化、大面积重写和意外删除要停下来问清。
TERMINAL

执行命令

运行测试、安装依赖，也可能删除数据或修改系统配置，必须重点审查。

高风险：不懂的命令不批准不要图省事长期开启无审查的全自动权限。
NETWORK / MCP

外部操作

访问网络或第三方服务，可能上传代码、读取外部数据，甚至创建真实资源。

检查：数据去哪、有何副作用？外部写入、部署、发消息等操作要单独确认。
Checkpoint 不等于 Git。 工具内的检查点适合撤销本次 Agent 修改；Git 才负责长期版本历史与团队协作。
官方资料[cite:4][cite:7][cite:8]
Codex 有审批模式，Claude Code 有权限规则和 Sandbox，Cursor 官方明确说明 Checkpoints 与 Git 分离。这里不要求记住具体设置位置，只建立“读、改、执行、外部操作”四种风险意识。

Git 负责让这些变化可追踪、可审查、可协作。

04 · Git ≠ GitHub

先分清：Git 是工具，GitHub 是平台

LOCAL VERSION CONTROL

Git

安装在电脑上的版本管理工具。

  • 记录每次提交和修改历史
  • 创建分支，支持并行开发
  • 查看差异，必要时回退版本
≠
REMOTE HOSTING PLATFORM

GitHub

托管 Git 仓库的在线协作平台。

  • 保存远程仓库和提交历史
  • 通过 PR 进行评审与合并
  • 使用 Issues 记录任务和问题

没有 GitHub 也能使用 Git；团队协作时，通常让本地 Git + 远程 GitHub配合。

Git 不是自动保存，也不是简单备份。GitHub 是常见的 Git 托管与协作平台。云端 Agent 可以直接围绕 Issue 和 PR 工作，但底层仍然需要理解版本、分支和评审。

04 · Core Concepts

Git 先记住三个词：仓库、提交、分支

REPOSITORY / REPO

仓库

一个由 Git 管理的项目，包含当前文件以及 Git 记录的历史信息。

理解：这是项目的“档案室”，不只是普通文件夹。
COMMIT

提交

一次带有说明、作者和时间的信息快照，用来记录一组有意义的修改。

理解：Agent 完成并验证一个小步骤后，留下存档点。
BRANCH

分支

一条独立的开发线，让你或 Agent 修改功能时不直接影响主分支。

理解：先在自己的线上改，验证后再合并。
Commit 不是按 Ctrl+S，也不是 Agent 每改一行就提交；它对应一个经过验证的小步骤。Branch 不是复制项目到另一个文件夹，而是 Git 管理的并行历史。

04 · Local → Remote

同一个修改：检查并提交，再同步到 GitHub

WORKING DIRECTORY

检查并暂存

git statusgit add <文件>

REMOTE REPOSITORY

远程同步

Clone 用于首次获取项目，Pull 取回队友更新，Push 上传本地已有提交。

git push
Commit 只存在本地，Push 后才到 GitHub。 开始新 Agent 任务前先同步；具体命令练习留到第二讲。
用刚才演示的登录表单修改继续操作：先 git status 和 Diff，再 git add <文件>、git commit -m "添加登录表单校验"、git push。补充说明 git clone 通常只做一次，之后用 git pull 获取更新。今天只听懂流程，第二讲再逐项练习和处理冲突。让 Agent 执行 Git 命令前，同样要检查命令、当前分支和工作区。

05

评审修改

队友查看代码，提出问题并继续改进。

06

合并主分支

确认通过后，把修改合入共同版本。

无论代码来自人还是 Agent，都要经过同样的验收与评审。 PR 让修改可见、可讨论、可追踪。
继续用刚才的登录表单校验修改：从功能分支 Push 到 GitHub，再发起 PR，描述修改内容、原因和测试结果。GitHub Copilot coding agent 和 Codex Cloud 都可以把任务结果带到 PR 流程，但自动创建 PR 不等于自动应该合并。

05 · Rules & Pitfalls

规范与常见误区

Agent 越快，越需要小步、审查和验证。
自动化程度越高，权限边界越重要。

05
两组误区分别对应 Agent 行动风险和团队协作风险。核心不是禁止使用自动化，而是知道自动化的边界在哪里。

05 · Agent Pitfalls

使用编程 Agent：四个必须避开的误区

01

一次派发整个项目

上下文和修改范围一起膨胀，出错后很难定位，也难以审查。

改成拆成有边界、有验收、能独立提交的小任务。
02

不给项目事实与规则

Agent 只能猜技术栈和目录约定，生成的修改可能南辕北辙。

改成提供相关文件、设计文档、项目规则和真实报错。
03

全自动批准，不看 Diff

无关重写、危险命令和敏感信息外发，都可能在无感中发生。

改成按风险授权，审查命令、修改范围和外部操作。
04

Agent 说完成就算完成

测试可能没跑、边界可能没测，甚至原有功能已经被破坏。

改成亲自核对测试与运行结果，通过后再 Commit 和 PR。

原则：Agent 可以自动行动，但人必须保留关键检查点。

可以对比两种提示：“帮我做完整个商城”与“先实现商品列表，字段按设计文档，完成后运行现有测试并展示 Diff”。后者边界、依据和验收都更明确。

05 · Git & GitHub Pitfalls

Git 与 GitHub：四个必须避开的误区

01

把密钥和 .env 提交上去

一旦推送，密钥可能已经泄露；仅删除文件不代表历史也干净。

改成提前配置 .gitignore；已泄露的密钥立即更换。
02

人或 Agent 直接修改 main

未验证的代码不断进入主分支，团队共同版本随时可能无法运行。

改成使用功能分支，经过验证、PR 和评审后合并。
03

不检查就盲目 git add .

可能把 Agent 生成的临时文件、构建产物和敏感信息一起提交。

改成先 git status 和查看差异，再选择需要提交的文件。
04

让 Agent 硬删或强制回退

可能把自己和队友的有效修改一起丢掉，让历史更加混乱。

改成先保留现场、看清双方差异，再讨论如何合并。

习惯：小步提交、写清说明、开始任务先同步、主分支只通过 PR 更新。

.gitignore 应尽早配置，典型忽略项包括 .env、node_modules、__pycache__ 和构建产物。禁止让 Agent 在未说明后果时执行 reset --hard、clean -f、push --force 等破坏性操作。
